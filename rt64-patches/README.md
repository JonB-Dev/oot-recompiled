# The renderer's patch series

The lighting track (`.scaffold/upgrades/phases.md`, phases 51 to 58) changes the renderer, and
`lib/rt64` is a pinned submodule that stays unmodified (`.scaffold/structure.md`: a local change
to `lib/` is a fork, which is a recorded decision, not a convenience). So every change to the
renderer is a patch in this folder, applied onto a fresh copy of the pinned tree at build time.

## How it works

- `tools/build_rt64.cmd` (phase 52) copies `lib/rt64` at its pinned SHA (`4337374`, the one
  `.scaffold/upgrades/stack.md` names) to `build-cmake/rt64-src/` and applies `rt64-patches/*.patch`
  in name order with `git apply`. It prints `RT64_SERIES_APPLIED <n> patches`, or
  `RT64_SERIES_CLEAN` when this folder holds no patch, and refuses with `RT64_PATCH_FAILED <name>`
  on the first hunk that does not apply. It never touches `lib/rt64`.
- `CMakeLists.txt` builds the renderer from `build-cmake/rt64-src/` when that folder exists and
  from `lib/rt64` otherwise, so a tree with no series builds exactly as it does today.
- `tools/rebuild_from_scratch.cmd` deletes the copy and reapplies the series, which is the proof
  that the series is the whole change.

## Rules for a patch

- Numbered and named for what it does: `0001-build-the-raytracing-path.patch`,
  `0002-raytracing-shader-cache-and-resources.patch`, and so on, in the order `phases.md` lists.
- Each patch is one phase's change, and the phase's commit carries it. A patch is never edited
  after its phase is committed; a correction is a later patch, so the series stays a history.
- The reasoning at the top of each patch as a comment block in the files it adds, in this
  project's voice, and a line here saying what it is for.
- Off is identical: with the ray tracing row Off, every capture in `build-cmake/harness/abshots/`
  matches the baseline taken in phase 51 (`tools/texture_compare.py` says `IDENTICAL`). A patch
  that changes the picture with the row Off is wrong, whatever else it does.
- On a renderer bump the series is rebased onto the new SHA by hand, patch by patch, and the SHA
  in `stack.md` and here is updated in the same commit. Until then the pin holds.

## How a patch is authored

`git clone --shared lib/rt64 build-cmake/rt64-work` (a scratch clone at the pin, ignored by
git), edit there, commit with the reasoning as the message, and export the commit with
`git format-patch -1 --stdout --no-signature --no-stat` into this folder under its number and
name. The message becomes the patch's preamble, which `git apply` skips and a reader does not.
`tools/build_rt64.cmd` applies the series with `git apply --directory=build-cmake/rt64-src`.
Paths inside a patch are relative to the renderer's root (`a/src/render/...`).

A change to plume (`src/contrib/plume`, the render abstraction) is authored in a second scratch
clone, `git clone --shared lib/rt64/src/contrib/plume build-cmake/plume-work`, because plume is
a submodule inside rt64 and the rt64 clone sees it as one pinned commit it cannot carry a diff
to. The commit is exported with the subdirectory on every path,
`git format-patch -1 --stdout --no-signature --no-stat --src-prefix=a/src/contrib/plume/ --dst-prefix=b/src/contrib/plume/`,
so the same apply step lands it in the mirrored copy beside the rt64 patches. Patch 0004 is the
first of these; its name says `plume`.

A patch may also carry a change to a pinned file when the phase needs one (0003 does, five
times; 0005 six): the change sits under `#if RT_ENABLED` or behind the runtime switch wherever it can,
is marked with the patch's number in a comment where it sits, and is listed in the table above,
so the Off proof stays the proof that nothing moved with the level Off.
